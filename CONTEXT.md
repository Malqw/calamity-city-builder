# Контекст для продолжения в Claude Code — Calamity City: билдер отрядов

Этот документ — для Claude (в Claude Code) или для человека, который продолжит
разработку без доступа к переписке, где всё это обсуждалось. Он описывает,
что это за проект, откуда взялись правила, что уже сделано, какие решения
были приняты и почему, и что осталось доделать.

## Что это за проект

Александр (пользователь) помогает другу тестировать домашний варгейм
**Calamity City** — кампейн-ориентированный PvPvE скирмиш про отряды с
суперсилами, сражающиеся друг с другом и с городскими бедствиями.
Первая задача была: собрать игровые ростеры (составы отрядов) для тестовой
партии вручную по дизайн-документу друга. Дизайн-документ было тяжело
парсить, поэтому родился билдер — интерактивный калькулятор, который сам
считает стоимость персонажей, производные характеристики, лимиты снаряжения
и т.д. по правилам из документа.

Дальше друг попросил на будущее два расширения: **админку** (редактировать
циферки/тексты сущностей без правки кода/yml) и **личный кабинет**
(сохранять и редактировать свои отряды). Сначала это было сделано как
Artifact на claude.ai (с капабилити `db`/`user`), но пользователь решил, что
Artifact не подходит для реализации (завязка на аккаунты claude.ai, нет
live-обновления, неудобно расшаривать вне организации) — поэтому проект
переехал на связку **Google Таблица (админка) + Google Apps Script (бэкенд)
+ статический сайт на GitHub Pages**. Именно эта версия — текущая и
единственная, которую стоит развивать дальше.

## Источник правил

Исходный дизайн-документ — `Диздок Calamity City 0.1.6.docx` (версия
обновляется, проверяйте дату файла), приложен рядом
(`source-docs/Диздок Calamity City 0.1.6.docx`) вместе с текстовым
извлечением (`source-docs/doc_text.txt`, через zipfile+ElementTree —
параграфы, включая ячейки таблиц). **Это единственный источник истины по
правилам** — если возникают вопросы по механике, сверяться нужно с ним, а
не с тем, что уже реализовано в билдере (в реализации есть осознанные
допущения — см. ниже). Когда друг присылает новую версию дизайн-документа,
замените файл в `source-docs/` и пересоздайте `doc_text.txt` тем же
способом, затем сверьте игровые данные в Google Таблице (не в коде!) построчно.
На 2026-09-22 таблица уже сверена с 0.1.6 (архетипы/роли/оружие/снаряжение/
глоссарий совпадают дословно; способности включают более поздние правки —
Ганката, Несгибаемый, Знание местности, Стальные мышцы, Вихрь).

Ключевая механика, которая уже понята и реализована:

- **Базовые параметры** персонажа: Сила (Might), Интеллект, Воля, Ловкость,
  Сражение, Стрельба — на лестнице кубов d6→d8→d10→d12.
- **Производные параметры**, считаются из базовых + размера + бонусов роли:
  - Защита = 4 (+1 если Сражение ≥ d8, +1 если Ловкость ≥ d8)
  - Броня = сумма бонусов от снаряжения/роли/размера
  - Здоровье = 2 (+1 за каждый параметр, достигший d8, ещё +1 за d12 —
    **кумулятивно по каждому параметру отдельно**, не один раз за
    персонажа — это неоднозначность в тексте документа, растолкованная в
    пользу кумулятивного чтения, см. «Допущения» ниже) (+бонусы роли/размера)
  - Скорость = 5 (+1 если Ловкость ≥ d10), у части ролей — жёсткий потолок 5
- **Известность (Known)** — очковая экономика для сборки отряда, по
  умолчанию бюджет 60 очков на отряд.
- **Три архетипа**, у каждого 4 роли (Командир / Ветеран / «тяжёлая»
  роль / Новобранец), разная стоимость/уровень/слоты способностей:
  - **Организация** — обычные люди, военные/наёмники/агенты.
  - **Одарённые** — мутанты/маги/вампиры и т.п., доступ к категориям
    способностей «Больше чем человек», «Духовные силы», «Манифестация».
  - **Тяжёлый отряд** — тяжёлая броня/мехи/крупные существа, у всех
    персонажей размера 3 автоматический бонус Броня+1/Здоровье+1
    («Неостановимая сила», реализовано как generic `sizeBonusRule` на
    архетипе, а не хардкод).
- **Справочник спецправил оружия**: Бронебойность, Пролом, Очередь,
  Надёжное, Блок, Перезарядка, Двуручное, Фокусированный огонь, Меткое,
  Лёгкое, Требует Параметр, Отталкивание.
- **Категории способностей**: обычные (Общие, Проворство, Мощь, Стратегия,
  Вдохновение, Беспощадность, Точность) и сверхъестественные (Больше чем
  человек, Духовные силы, Манифестация — доступны Одарённым/Тяжёлому отряду).
  У способностей из «Духовные силы»/«Манифестация» есть игровая стоимость
  в Очках Мотивации (внутриигровой ресурс во время партии) — это **не**
  Известность и билдер её сознательно не считает при сборке, только
  показывает текстом.

## Архитектура текущей (актуальной) версии

```
index.html  (статический сайт, без сервера, ванильный JS, без фреймворков)
   │  fetch() при загрузке
   ▼
Google Apps Script Web App (apps-script/Code.gs)
   │  читает/пишет
   ▼
Google Таблица (7 вкладок с игровыми данными + 1 вкладка «Отряды»)
```

- **`index.html`** — весь билдер в одном файле (инлайновые `<style>` и
  `<script>`), ~1400 строк JS. Ключевые части:
  - `DEFAULT_DATA` — зашитая копия игровых данных (оружие/снаряжение/
    способности/архетипы-роли/глоссарий) как офлайн-фолбэк на случай,
    если `API_URL` пуст или сервер недоступен. Показывается баннер
    предупреждения (`renderDataBanner`).
  - `API_URL` — вписан URL реально развёрнутого Apps Script (см. ниже).
  - `data()` — возвращает `liveData` (если получены с сервера) либо
    `DEFAULT_DATA`.
  - `currentArchetype()`, `role()`, `roleCategories()`, `factionOk(item)` —
    архетип-агностичные хелперы; вся отрисовка/подсчёт идёт через них, а
    не через хардкод `organization`.
  - **Вход/личность**: обязательная модалка при первом заходе (имя + код
    доступа), дальше кэшируется в `localStorage` (`identity`,
    `LS_IDENTITY_KEY`) и не спрашивается повторно. Меняется по ссылке
    «сменить» на вкладке «Мои отряды» (`App.openModal('login')`).
  - **«Мои отряды»** — домашний экран после входа: список сохранённых
    отрядов + «Создать отряд». Из билдера есть кнопка «← Все отряды»
    в тулбаре, чтобы вернуться к списку.
  - **Модальные окна выбора** (способности/оружие/снаряжение/арсенал) —
    единый оверлей `#modal-overlay` вне дерева `#view-builder`, чтобы
    пережить `renderAll()`. `App.openModal(kind, unitId)` /
    `App.closeModal()`, содержимое строит `renderModalContent()` по
    `activeModal.kind`; после любой мутации `renderAll()` сам вызывает
    `refreshModal()`, чтобы открытая модалка обновилась вместе с
    карточкой. Списки — аккордеоны (`accHead`/`accAction`/`qtyAction`):
    клик по позиции разворачивает характеристики/описание и кнопку
    добавить/убрать; спецправила оружия — отдельные «пилюли» (`kwChips`)
    с тултипом из глоссария по наведению/тапу.
  - **Арсенал отряда** (`state.arsenal`) — оружие/снаряжение хранится не
    как список id на юните, а как отдельные экземпляры
    `{id, itemId, kind:'ranged'|'melee'|'equipment', ownerId:null|unitId}`.
    Пока `ownerId===null` — предмет «трофей», не входит в Известность
    отряда (см. `squadTotals`/`computeUnit`); как только он выдан
    персонажу — считается. Один и тот же `itemId` может встречаться
    несколько раз (дубликаты, например два пистолета).
    **Осознанно нет лимита «рук»/двуручности** — сколько бы оружия ни
    нёс персонаж, единственное ограничение — слоты инвентаря
    (`fitReasons()`/`canEquipNow()`); двуручное просто занимает 2 слота
    вместо 1, не вытесняя ничего. Никакого автозамещения нигде нет —
    если предмет не помещается (не хватает слотов, либо у персонажа уже
    есть другое защитное снаряжение — единственное исключение, это
    правило самого предмета брони, а не рук), кнопки «Добавить»/«Взять
    из арсенала» просто неактивны с пояснением причины. `uniqueMax`
    считается по **всему** арсеналу, не только выданному.
    Действия с экземплярами: `App.unitAddNew` (создать новый и сразу
    выдать, тратит `uniqueMax`) / `App.unitTakeFree` (взять уже
    существующий свободный экземпляр, `uniqueMax` не трогает) /
    `App.unitRemoveItem` («Удалить» — выкинуть совсем) /
    `App.unitStash` («В арсенал» — просто снять, экземпляр остаётся в
    общем пуле). У снаряжения/оружия в модалках эти четыре действия
    показаны отдельными кнопками (`qtyAction`). Броня теперь тоже через
    свою модалку (`App.openModal('armor', unitId)`), не через `<select>`
    — те же action’ы, просто максимум одна единица зараз (проверяется в
    `fitReasons`). Отдельно — модалка «Арсенал» на весь отряд:
    `App.arsenalAdd` / `App.arsenalGive` / `App.arsenalDiscard`.
  - **Прогрессия/опыт** (`LEVEL_TABLE`, уровни 2–16 из диздока) — у
    юнита есть `level` (стартует от `role.level`), `xp`, и накопленные
    бонусы `bonusStat`/`bonusArchetype`/`bonusAny`/`knownBonus`/
    `heroicRoll`. `App.levelUp(unitId, choice?)` тратит опыт и выдаёт
    бонус уровня (`choice` нужен только для уровней типа `'choice'` —
    игрок сам решает параметр или способность). Общий опыт отряда —
    `state.campaignXp`, переносится бойцу через `App.transferXp`.
    `archSlots()`/`anySlots()` — обёртки над `r.archetypeAbilitySlots`/
    `r.anyAbilitySlots` с учётом бонусов уровня; везде в рендере и
    валидации способностей используются они, а не сырые поля роли.
  - `computeUnit(unit)` — считает все производные характеристики и
    стоимость персонажа по содержимому арсенала (не по полям юнита);
    учитывает `sizeBonusRule` архетипа и `knownBonus` от прокачки.
  - `squadTotals()` / `squadIssues()` — валидация бюджета, лимитов ролей,
    senior/novice баланса (через `tier` на роли), лимитов уникальных
    предметов (считает по всему `state.arsenal`).
  - `App.saveSquad` / `App.loadSquad` / `App.deleteSquad` /
    `loadMySquads()` ходят на `API_URL` через `apiPost()`; сохраняют
    также `arsenal` и `campaignXp`. `App.loadSquad` при загрузке
    **мигрирует** старые отряды (сохранённые до появления арсенала, у
    которых оружие/снаряжение сидело прямо в массивах юнита) —
    переносит их в `state.arsenal` с `ownerId` того же юнита, так что
    старые сохранения не выглядят «голыми» после обновления кода.
  - Печать: `App.printSquad()` — сеточная раскладка карточки (шапка
    Имя/Тип/Размер/Уровень/Опыт/Известность, левая колонка производных
    параметров, таблица оружия с фиксированной шириной колонок и
    переносом текста), плюс отдельная страница «Справочник ростера»
    (ключевые слова/способности/снаряжение, только то, что реально
    используется в отряде, без брони/рюкзака/«Требует Параметр») и
    строка «Резерв отряда» для невыданных трофеев.
  - Состояние текущего собираемого отряда персистится в `localStorage`
    (`LS_STATE_KEY`) при каждой мутации (`persistHot()` — это специально
    вызывается из всех `App.*`-мутаторов, включая `setSize`/`stepStat`,
    раньше там был баг с потерей несохранённых правок при перезагрузке).
  - **Админки внутри сайта нет** — правка данных происходит прямо в
    Google Таблице.

- **`apps-script/Code.gs`** — бэкенд:
  - `SEED_DATA` — та же игровая база данных, что раньше была `DEFAULT_DATA`
    на сайте (сейчас это единственное «истинное» место для стартовых
    значений — при первом запуске `seedAll()` раскладывает её по вкладкам
    таблицы; дальше источник истины — сами ячейки таблицы, не этот объект).
  - `seedAll()` / `seedWeapons/Equipment/Abilities/Glossary/
    ArchetypesAndRoles/SpecialRules()` — создают вкладки с понятными
    русскими заголовками колонок и заполняют их **только если вкладка
    пустая** (не перезатирают правки).
  - `buildGameData()` — читает все вкладки и пересобирает ровно ту же
    вложенную JSON-структуру, что была в `DEFAULT_DATA` (архетипы→роли,
    спецправила по архетипу, splitlist для traits/categories и т.д.).
  - `doGet(e)` — отдаёт `{ok:true, data: buildGameData()}`; на `?action=ping`
    отвечает `{ok:true, ping:'pong'}`.
  - `doPost(e)` — `action` = `listSquads` / `saveSquad` / `deleteSquad`,
    работает с вкладкой «Отряды» (id, ownerName, accessCode, squadName,
    archetype, budget, unitsJson, updatedAt, **arsenalJson, campaignXp** —
    последние два столбца добавлены для арсенала/опыта). Есть проверка,
    что при обновлении/удалении чужой id нельзя перезаписать без
    совпадения имя+код (`normName_` — сравнение регистронезависимое по
    имени). `ensureSquadsSheet()` вызывается на каждый `doPost` и сама
    дописывает недостающие колонки справа, если лист «Отряды» был создан
    до появления арсенала — старые строки не трогает, просто не имеют
    значений в новых столбцах (читаются как `[]`/`0`).
  - **CORS-нюанс**: фронтенд шлёт POST как обычную строку (без явного
    `Content-Type: application/json`), чтобы браузер не делал preflight —
    Apps Script Web Apps не обрабатывают `OPTIONS`. Если будете менять
    формат запросов — не потеряйте это ограничение.

- **`README.md`** — пошаговая инструкция по деплою (создание таблицы,
  вставка `Code.gs`, разворачивание веб-приложения с доступом «Все»,
  вписывание `API_URL` в `index.html`, заливка на GitHub Pages).

## Что уже сделано и проверено

- Полный трёхархетипный билдер (Организация/Одарённые/Тяжёлый отряд) с
  фильтрацией оружия/снаряжения по `faction`, архетип-специфичными
  спецправилами и категориями способностей.
- **Задеплоено и живёт по-настоящему**: Apps Script развёрнут (URL уже
  вписан в `API_URL`), таблица данных ведётся пользователем, сайт лежит
  на GitHub Pages — `https://malqw.github.io/calamity-city-builder/`
  (репозиторий `Malqw/calamity-city-builder`, ветка `main`, root).
  `git init` сделан именно в `D:\calamity-builder` (а не в общей папке
  сессии); `source-docs/`, `history/` — в `.gitignore`, в публичный репо
  не пушатся.
- Round-trip тест: `seedAll()` → `buildGameData()` даёт **побайтово** тот
  же JSON, что и исходный `SEED_DATA` (прогонялось через Node с
  фейковыми шимами `SpreadsheetApp`/`ContentService`/`Utilities` —
  скрипт теста не сохранён в проекте, но логика воспроизводима).
- Флоу «Мои отряды»: вход по имени+коду (кэш в `localStorage`), список,
  создание, сохранение/обновление, удаление — включая проверку, что
  чужим кодом доступа нельзя перезаписать/удалить чужой отряд.
- Модалки выбора способностей/оружия/снаряжения + отдельная модалка
  «Арсенал» (трофеи кампании, выдача персонажам, лимиты дубликатов) —
  проверено небольшим нативным юнит-тестом на Node (эмуляция DOM/
  localStorage/fetch без браузера, скрипт временный, в проекте не
  сохранён): создание юнитов, экипировка дубликатов (два пистолета),
  замена одноручного оружия двуручным (снятые предметы возвращаются в
  арсенал, а не исчезают), `uniqueMax` на весь арсенал, прокачка по
  `LEVEL_TABLE` (включая уровни с выбором игрока), перенос опыта отряда
  бойцу, печать без падений на пустом/заполненном отряде.
- Печать (`App.printSquad`): сеточная карточка бойца + отдельная
  страница-справочник по ростеру; таблица оружия не расползается вширь
  на длинных названиях (антиматериальная винтовка и т.п.).

## Допущения билдера (стоит свериться с автором правил при случае)

Список показывается прямо на сайте в карточке «Допущения билдера», но
продублирую здесь:

1. Тяжёлый Ветеран считается «Ветераном» для лимита Новобранцев и для
   спецправил «Специалисты широкого профиля» / «Цепочка командования».
2. Лимиты на дальнобойное и ближнее Двуручное оружие независимы — можно
   одновременно нести двуручное дальнобойное и двуручное ближнего боя.
3. Здоровье от «достижения д8/д12 в базовом параметре» считается
   отдельно для каждого параметра (кумулятивно), а не один раз за
   профиль — текст документа здесь неоднозначен, выбрана кумулятивная
   трактовка как более согласованная с фразой «все производные параметры
   кумулятивны» из документа.
4. Броня, рюкзак, мультитул и подобное «пассивное» снаряжение не
   занимает слот инвентаря, если это не указано явно в тексте предмета.

Есть и более локальные ручные допущения (не автоматизированы в билдере,
только текстовые пометки):
- «Специалисты широкого профиля» (Организация): Командир/Ветеран может
  вручную выбрать ещё одну категорию способностей — билдер это не
  проверяет автоматически.
- Тяжёлый Новобранец (Одарённые) получает бесплатную встроенную
  способность категории «Больше чем человек» вне лимита слотов —
  впишите вручную, билдер не считает это в лимит.
- «Оружие, наделённое силой» (предмет `empowered_weapon`, Одарённые) —
  апгрейд для ОДНОГО оружия персонажа, привязывается вручную, билдер не
  трогает конкретное оружие автоматически.

## Решения по арсеналу/прогрессии (согласовано с пользователем 2026-09-22)

- Диздок описывает и опыт/прогрессию персонажа по уровням (таблица
  «Прогрессия персонажа»), и намекает на трофеи из кампании — в билдере
  этого не было вообще, добавлено в этой сессии.
- **Экономика арсенала**: предмет в арсенале, пока не выдан персонажу, не
  тратит Известность отряда вообще (это «трофей, лежащий в грузовике»).
  Как только предмет назначен персонажу — его стоимость сразу входит в
  Известность персонажа/отряда. Это осознанное решение пользователя, не
  выведено из текста диздока напрямую (там нет отдельной механики
  «арсенала» — она изобретена билдером для удобства кампании).
- **Старые сохранённые отряды** (формат до арсенала/опыта, оружие/
  снаряжение массивом прямо на юните) — по решению пользователя жёсткая
  миграция сейчас не нужна («пока да, но в будущем надо будет более
  аккуратно»). Сделан мягкий best-effort перенос в `App.loadSquad`
  (см. выше) — старые отряды не «голые» после обновления, но это не
  формальная версионированная миграция; если формат снова поменяется,
  этот вопрос стоит поднять снова, а не тихо доусложнять `loadSquad`.

## Известные ограничения текущей реализации

- **Безопасность «личного кабинета» номинальная**: код доступа хранится
  в Google Таблице открытым текстом, защита — только «кто не знает пару
  имя+код, не увидит/не сотрёт чужой отряд». Осознанный компромисс ради
  простоты для тестовой группы друзей, не для публичного продукта.
- **Нет live-синхронизации**: и игровые данные, и список «моих отрядов»
  подтягиваются одноразовым fetch/POST при заходе на вкладку/загрузке
  страницы — если кто-то поменял таблицу, пока у вас открыта страница,
  нужно её перезагрузить.
- **Apps Script бесплатные лимиты**: ~20000 запросов/день на аккаунт —
  для тестовой группы с большим запасом, но если проект вырастет
  (публичный релиз, много игроков), это может стать узким местом — тогда
  стоит рассмотреть Supabase/Firebase (обсуждались как альтернативы, см.
  раздел «Что рассматривали и отклонили» ниже).
- Печать/PDF (`App.printSquad`) не менялась в этой миграции — использует
  `window.open` + `document.write`, актуальность не проверялась после
  переезда с Artifact (стоит перепроверить, если печать окажется нужна).

## Что рассматривали и отклонили

При выборе архитектуры пользователю предлагались варианты (в порядке от
простого к сложному): таблица-как-БД (Sheets/Airtable) без своего бэкенда;
свой сайт + Supabase/Firebase (полноценные аккаунты и роли); Discord-бот
(если тестовая группа сидит в Discord); полный кастомный стек
(Node/Python backend + своя БД + хостинг). Выбор пал на связку
**Google Sheets + Apps Script + GitHub Pages** осознанно, по трём
критериям пользователя: минимум возни, друг правит данные без какого-либо
кода (прямо в таблице), простая авторизация имя+код без реального логина.
Если требования изменятся (нужен реальный логин, много одновременных
редакторов, публичный релиз игры) — стоит пересмотреть в сторону
Supabase/Firebase, не откатываться на Artifact.
